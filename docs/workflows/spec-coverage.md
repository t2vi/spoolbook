# Spec coverage workflow — 100% requirements, traced to tests

<!-- OAIKit template. Fill in the two "per project" tables; everything else is shared. -->

**Kicks in when:** `spec-coverage` is enabled in `.claude/profile.yaml` (default alongside `coding`), for every task `coding.md` handles. The on-demand audit is `/spec-audit`; the
tripwire and bug rules apply in every phase of every task.

**Goal:** every shipped surface is covered by a spec, every requirement states its observable
effect, and every requirement is verified by a test **at the lowest layer that can prove it**.
Shift left: a bug should be caught at the requirement (the spec says what must happen), then
by the cheapest test that checks it, never first by a user.

Spec-kit projects keep specs as `specs/NNN-*/spec.md`; others use whatever spec/PRD format the
project has. Everything below works with either — "FR" means an individually numbered
requirement in that document.

## The ledger — `specs/COVERAGE.md`

The single place where "100%" is measured. Regenerated by `/spec-audit`; never hand-maintained
beyond the notes columns.

1. **Surfaces → specs**. One row per shipped surface: `Kind | Surface | Spec(s) | Status | Notes`.
   - ✅ covered — a spec states what it does (its observable effect).
   - 🟡 partial — a spec mentions it but not its effect (e.g. "the setting is exposed" —
     the classic way a setting that does nothing ships unnoticed), or covers only part.
   - ❌ none — no spec.
2. **Requirements → tests**. One row per FR: `Spec | FR | Verify (planned) | unit | integration | api | e2e | Status`.
   - ✅ tested at (at least) its planned layer · 🟡 tested only at a different/higher layer, or
     linked only by inference · ❌ no test.
3. **Gaps** — open gaps grouped by area, each with its issue link.
4. **Escapes** — every bug found after merge: `Bug | FR | Found at | Should have been caught at | Test added`.
   "Found at" is one of `spec`, `unit`, `integration`, `api`, `e2e`, `review`, `live`, `user`. The
   trend to watch is escapes moving left.
5. **Summary** — surface coverage %, FR test coverage %, FR-at-planned-layer %, date and commit.

## Conventions

- **Every FR states effect + verification.** End each FR with `*Verify: <layer>[, <layer>]*`,
  naming the lowest layer(s) that can prove it. A setting, toggle, flag or env var FR states what
  it changes at runtime, not only that it can be read or written.
- **Tests carry the FR they prove**: a comment directly above the test, e.g.
  `// spec: 007/FR-001a` (Rust/TS), `# spec: 005/FR-008` (Hurl). Several are comma-separated.
  Tags are authoritative. Test references that already appear in a spec's `tasks.md` (e.g.
  `tests/sync.rs:491`) count as *inferred* links (🟡) until tagged.
- **Layers — fill in per project** (delete rows that don't exist):

  | Layer | Where (example) |
  |---|---|
  | unit | inline/colocated unit tests (`src/**/*.test.ts`, `#[cfg(test)]`) |
  | integration | service-level tests against a real router/DB (`tests/`) |
  | api | black-box HTTP tests against a running server (Hurl, Postman) |
  | e2e | browser/UI tests against the full stack (Playwright) |
  | live (not counted) | on-demand checks against real third-party services |

- **Surface sources — fill in per project**: the files the audit enumerates, one row per kind
  of shipped surface. Typical kinds: API route, page/screen, background job, setting, env var,
  CLI command, plugin/extension, migration, script, public library export. For each, name the
  file(s) and pattern that list them (e.g. "every `.route(` in `src/api/*.rs`"). The audit
  reads *this table*, so a missing row is an invisible blind spot. Keep it current.

## `/spec-audit` — the scan

Modes:

- **`full`** (default, on demand): enumerate all surfaces and FRs, rebuild `COVERAGE.md`, file
  or update one gap issue per area (the project's documentation label), report the % and what changed since
  the last ledger.
- **`diff <base>`** (feature-ready): only surfaces and tests touched between `<base>` and HEAD.
  Every new or changed surface must map to a spec (✅), and every FR the diff touches must have a
  test at its planned layer. Fails with the list otherwise.
- **`release`** (release prep): `full`, then the **ratchet** against the last release tag's
  ledger. It fails if a surface added since the tag is ❌, or if the number of untested FRs went
  up. Old gaps don't block a release; coverage never goes down. Prints the coverage line for the
  release notes.

Filling gaps: a gap in shipped behavior gets a *retroactive* spec (`spec.md` only,
`Status: Implemented (retroactive spec — see Notes)`, behavior verified from the code, FRs with
Verify lines). Burn down in risk order: settings and background jobs → data-changing routes →
read-only routes → UI. One area per session is fine; the ledger shows the trend.

## Tripwire — noticing unspecced behavior in any phase

Whenever you read or touch behavior while exploring, planning, debugging, reviewing or
implementing, and no spec covers it:

- **Not what the current task changes** → don't derail. Mark or add its `COVERAGE.md` row ❌/🟡,
  add it to the area's open gap issue (create one if none), and list it under **Unspecced
  found** in the end-of-task report.
- **The current task changes it** → write the retroactive spec (or add the missing FR to the
  covering spec) *before* changing the behavior, so the change is reviewed against a stated
  requirement.

## Bugs — escape analysis

`coding.md`'s "every bug lands in a spec" rule, plus one step: record the bug in the
**Escapes** table, name the layer that *should* have caught it (the lowest one that could), and
add the regression test there, tagged with the FR. If the answer is "spec", the fix starts with
correcting the FR.

## README & docs-site staleness

`/spec-audit` only checks surface↔spec↔test coverage — it doesn't read prose. Whenever an FR
or a spec changes (new, corrected, or amended), that's also a trigger to check `README.md` —
and the project's docs-site pages, if it has one (`docs-site/` or equivalent, see
`docs-site.md`) — for a description of the behavior that FR/spec just changed. Update it in
the same pass; don't defer to the Release Checklist's "always review" step (which is the
backstop for what this trigger misses, not the only check).

**Manual sweep**: since this is a prose check, not a mechanical one, it's easy for it to lag
behind several spec changes in a row. Periodically (e.g. once a release, or after several
specs have landed since the last sweep) run a manual pass: read the README/docs-site sections
that describe FR-covered behavior against the current spec set and correct drift, independent
of whether any single change triggered it.

**Version strings are a separate, mechanical case of this**, not tied to any FR/spec change: a
README badge line or docs-site page often hardcodes the version as plain text, not read from
the project's `VERSION`/manifest file, so it drifts silently every release unless grepped for
— see `CLAUDE.md`'s Release Checklist step 7.
